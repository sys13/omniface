Define the operation once.Prove every interface agrees.

facet is a TypeScript framework where your REST API, TypeScript SDK, CLI and MCP server are all facets of one protocol-neutral definition. Auth, rate limits, idempotency, error shapes and pagination run in a single pipeline behind all four — so a new interface cannot quietly skip them, and no two can drift apart.

The definition writes the tests as well. The example app's ten operations become 44 conformance cases that call each op on every interface it reaches and fail if any two disagree — nobody typed one of them. The full suite is 425 tests, green on 19 September 2026.

The problem · five copies of one contract

The interfaces agree, right up until the day they don't.

An app that wants to be reachable by people, scripts, services and agents ends up hand-building the same contract five times: a REST API, an SDK per language, a CLI, an MCP server, maybe webhooks. Each copy re-implements auth, rate limits, error shapes and pagination slightly differently. None of that is hard. It is just five places to change, and four of them are where a fix goes missing.

Here is what you would reach for instead, what each one is genuinely good at, and where facet's mechanism differs. Nothing in this table rests on a competitor lacking something — it is a difference of shape, and those hold up.

You'd otherwise…What it's good atWhere the shape differs
Hand-build each interface Total control, no abstraction to learn, and the fastest possible first endpoint. One definition, four projections, and a generated suite that fails when any two of them answer differently.
Generate SDKs from OpenAPI
Stainless · Speakeasy · Fern		 Excellent, idiomatic SDKs in many languages, from a document you already publish. The core here is operations, not endpoints — so REST is one projection among four rather than the source every other interface inherits its shape from.
A typed RPC runtime
tRPC · oRPC		 A superb runtime with end-to-end inference and almost no ceremony. The same runtime-first stance, projected onto four interfaces at once, with cross-cutting concerns as plugins in one pipeline instead of per-interface middleware.
An interface definition language
Smithy · TypeSpec		 One spec, many emitters, and a mature model that has survived very large APIs. The spec is a typed TypeScript value, not a separate language: the server interprets it at runtime, and codegen is reserved for things that run elsewhere — SDKs, the CLI, OpenAPI, docs.
A plugin-shaped auth library
Better Auth		 The right plugin model, and the reason facet's looks the way it does. The same model widened past one concern: logging, API keys, scopes, rate limits, idempotency, audit and telemetry are all plugins in the same pipeline.
The shape · four layers, no YAML

Types, operations, facets, plugins.

Everything is code. There is no separate IDL and no YAML — the spec is a typed TypeScript value, and openapi.json is an output. A typo in a facet override fails tsc, not a linter at runtime.

  • types
    Fields, once

    Standard Schema underneath — Zod, Valibot, ArkType — with facet traits layered on top. Field traits like pii and internal survive .pick(), .extend() and .nullable().

  • ops
    Verbs over types

    Protocol-neutral. Not endpoints, not tools. If REST shapes the core, every other facet inherits REST's shape — so it doesn't.

  • facets
    Per-interface views

    Opt in per interface. Conventions first: tasks.complete becomes POST /tasks/{id}/complete, tasks complete <id>, tasks_complete and client.tasks.complete(). Typed overrides second, and rare on purpose.

  • plugins
    Cross-cutting concerns

    Schema, context, hooks, ops and per-facet adapters. One concern, one plugin, four interfaces.

The whole app, in one file
import { facet } from 'omniface'
import { apiKeys, logging, rateLimit, scopes } from 'omniface/plugins'
import { t } from 'omniface/zod'

const Task = t.named('Task', z.object({
  id: t.id(),
  title: z.string().min(1),
  ownerEmail: t(z.email(), { pii: true }),
}))

const f = facet({ plugins: [
  logging(), apiKeys({ keys }), scopes(),
  rateLimit({ limit: '100/min' }),
] })

export default f.app({
  name: 'acme',
  ops: {
    tasks: {
      create: f
        .op({ input: Task.pick({ title: true }), output: Task })
        .traits({ scope: 'tasks:write' })
        .handle(({ input, ctx }) => {
          ctx.log('creating task') // typed: from logging()
          return db.tasks.insert(input)
        }),
    },
  },
  facets: {
    rest: true,
    sdk: true,
    // a typo in the op id below fails tsc
    cli: { ops: { 'tasks.create': { args: ['title'] } } },
    mcp: true,
  },
})
Traits · intent in, behaviour out

One word on the op. Five things downstream, and one rule behind them.

A trait carries intent; each facet decides how to present it. The important half is the last card: the behaviour itself is written once, in the pipeline, where every interface runs it. idempotent: true was advertised and unenforced once — now one plugin fills the pipeline's idempotency stage and all four facets inherit it.

REST
Idempotency-Key: <key>

A request header, the way every API you already call does it.

SDK
one key per logical call

Minted automatically and reused across the client's own retries.

CLI
--idempotency-key <key>

To pin one key across separate runs of a script.

MCP
_meta["facet/idempotency-key"]

In the tool call's metadata, plus the matching tool hint for the model.

The pipeline
fingerprint(validated input)

The key is scoped to its op and fingerprinted over the validated input, so the same logical call hashes the same whichever facet it arrived on. Reusing a key with different input is a conflict. A failed call leaves no record, so only successes replay.

The other traits work the same way. destructive makes the CLI confirm before running. readonly makes the conformance suite demand that all four facets return the same value, not merely the same shape. scope makes every facet refuse an anonymous caller — and if an op declares a scope that no installed plugin enforces, the app refuses to start rather than advertising a guarantee it isn't keeping.

Plugins · one pipeline, no side doors

A new facet can't bypass auth, because facets don't decide.

Concerns run in the operation pipeline, not in the interface. Eight plugins ship today — logging, apiKeys, auth, scopes, rateLimit, idempotency, audit and otel — and adding rateLimit() changes all four interfaces at once, which is asserted by a test rather than assumed.

A plugin reaches an interface through exactly one slot: adapters. It can find a credential, attribute a caller, add namespaced routes, commands, flags and options, and decorate an answer. It is never handed an invocation, so it can never decide whether an operation runs. Plugin routes live under /_<plugin>, so a plugin cannot shadow an op's route; a contributed CLI command is an alias for an op, not a side door around one; and a flag that would shadow a built-in one is a startup error.

Identity works the same way. One AuthAdapter contract fills the pipeline's authenticate stage for every facet at once, with API keys, JWT (issuer and JWKS, verified with WebCrypto), Better Auth, Clerk and WorkOS implementations that pull in no provider SDK. Several run side by side; each declines what is not its own, so an API key, a browser session and a machine JWT can live on one app. A credential that is an adapter's shape and fails verification is rejected there and then — a forged token never falls through and lands as anonymous.

The adapters slot · presentation, never decision
definePlugin({
  name: 'sessions',
  // the decision: every facet, once
  hooks: { authenticate: verifySession },
  // the presentation: per facet, never a decision
  adapters: {
    rest: {
      credential: (request) => cookieToken(request),
      routes: [{ method: 'POST', path: '/login',
                 handler: login }], // → /_sessions/login
      securitySchemes: { sessionCookie: {
        type: 'apiKey', in: 'cookie', name: 'session' } },
    },
    mcp: { instructions: 'Log in first.' },
    cli: { flags: [{ name: 'session', credential: true,
                     env: 'ACME_SESSION' }] },
    sdk: { options: [{ name: 'sessionToken',
                       credential: true }] },
  },
})

The CLI and the SDK run in another process, so what a plugin declares for them travels in the manifest.

Proof · generated, not asserted

The definition writes the tests that check the definition.

"Every interface agrees" is the whole claim, so it is the thing that has to be mechanically checked rather than believed. conformanceCases() reads the definition and emits the suite: for every op, on every facet it reaches, a contract check — projection, bindings, advertised fields, name collisions, no internal fields leaking — plus the call-based checks its traits imply. Adding an op adds its cases. You never write one.

Every figure on this page came out of a command run in this repository on 19 September 2026: pnpm check for the test count, omniface conformance src/app.ts for the case count, omniface build for the op count. If you change the example app, those numbers move — which is the point, and also why none of them is typed into the copy from memory.

And "is this breaking?" is a command, answered once per facet.

A breaking change is rarely breaking everywhere. Renaming an output type breaks the SDK and nothing else. Marking an op destructive breaks unattended CLI scripts and nothing else. omniface diff compares two manifests and says which, and --strict turns a breaking change into an exit code. The example app's CI is omniface lint && omniface conformance --strict.

Quickstart · definition to four running interfaces

Seven commands, and none of them is a code generator you have to babysit.

A .ts entry needs a runtime that strips types — Node 22.18+, Node 24 or Bun. On Node 20 the same commands point at compiled JavaScript.

Run all four interfaces at onceREST on :3000, MCP at /mcp, and an inspector page at /_omniface.
npx omniface dev app.ts
Look at one op on every facetThe command from the top of this page.
npx omniface inspect app.ts tasks.create
Build the outputs.omniface/ gets a manifest, openapi.json, llms.txt and a CLI — shipped as an engine plus a manifest, not a pile of generated commands.
npx omniface build app.ts
node .omniface/cli/bin.mjs tasks create "Hello"
Serve it to an agentMCP over stdio, or Streamable HTTP from dev.
npx omniface mcp app.ts
Keep the definition honest--fix writes the t.named() the named-type rules ask for, then re-lints in a fresh process to check its own edit — an edit that doesn't load, or doesn't resolve the finding it was for, is restored.
npx omniface lint app.ts --fix
Prove the facets still agree, and see what brokeWith no setup at all, conformance runs the checks that read the manifest; a conformance.fixtures.ts beside the entry unlocks the rest.
npx omniface conformance app.ts
npx omniface diff .omniface/manifest.json app.ts
Scope · what this is not, today

The honest boundaries.

Every one of these is a real limit right now, not a coming-soon. If one of them is your requirement, this is the wrong tool and you should find that out from this page rather than from the install.

not yet

Not on npm

The name facet belongs to an unrelated package and the @facet scope is unclaimed. The release pipeline exists — changesets, provenance, tags — with nothing published through it.

not proven

No second language, demonstrated

omniface build writes a publishable TypeScript package to .omniface/sdk/, and examples/tasks/sdks/ carries starting configurations for Stainless, Fern, Speakeasy and openapi-generator. None of them runs in CI, so agreement in a second language is argued rather than demonstrated.

not yet

Auth presentation isn't wired

The adapters slot it needs now exists, but the SDK constructor, a CLI login device flow and MCP OAuth 2.1 are not connected to it.

not this

Request/response only

No streaming, no long-running operations, no webhooks and no events. Every op is one call in, one answer out.

not this

TypeScript, on a server

Definitions are TypeScript and the runtime interprets them in Node or Bun. Other languages are somebody else’s generator reading the OpenAPI document — a deliberate split, not a stopgap.

not proven

No comparison benchmark

There is no control arm — no "same API, hand-built, measured" run — so there is no N× less code or N× faster claim anywhere on this page. The numbers here are all about this repository's own test suite.

One more boundary worth stating plainly: this is an early MVP. Core, REST, MCP, the TypeScript SDK, the CLI engine, eight plugins and five auth adapters work end to end and are tested that way, but the vocabulary and the CLI can still change. What the tests hold stable is the part you would actually notice — that the four interfaces agree, and that the conformance suite fails when they stop agreeing.
